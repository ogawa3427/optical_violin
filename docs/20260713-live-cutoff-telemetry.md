# 2026-07-13 ライブ音切れ調査と修正 + テレメトリ基盤

実機 (AtomS3R) 演奏で「音がたまに変に切れる」報告を、この日に新設したテレメトリ基盤で
定量調査し、原因 3 系統を切り分けて 2 系統を修正した。あわせて KRR 推論を高速化した。

## 0. テレメトリ基盤 (新規)

- **Core 分割**: 演奏パス (HID→CausalEngine→MIDI) は Core 1 専有のまま、Core 0 に
  テレメトリタスクを新設 (`src/io/telemetry.{h,cpp}`)。LCD 状態表示 (10fps, M5Canvas) と
  PC 向け CSV (USB CDC) を担当。演奏パスからは FreeRTOS キュー投入のみ (満杯時は捨てる)。
- **レイテンシ計測**: `ESP.getCycleCount()` (240MHz → 4.17ns/cycle) でパルス受信→expr 確定
  (infer_ns) と →CC#11 送出完了 (send_ns) を毎パルス記録。
- **PC 受け**: `tools/watch_telemetry.py` (pyserial)。ライブ監視 + `tools/logs/` へ全行記録 +
  ノート完成ごとのサマリ表示 + `--analyze` で事後再集計。
- **ハマった点 (両方修正済み)**:
  1. Core 1 の `NOTE_ON/OFF` ログと Core 0 の CSV が CDC 上で混線 → ライブモードでは
     Core 1 からの Serial print を全廃 (`output.cpp` を `#ifndef M62_LIVE_HID` ガード)。
  2. パルス用とノート境界用で **キューを 2 本に分けると吸い上げ順で時系列が壊れる**
     (NoteOff が次ノートのパルスより後に出力され、PC 側集計に幽霊ノートが湧く)。
     → P/N 混載の**単一キュー**に統一。教訓: 順序が意味を持つテレメトリはキュー 1 本。

## 1. 音切れの原因 3 系統

テレメトリのノート別サマリ (dur, Δt 列, off 理由) から切り分けた。

### (a) 1 秒の壁 — WINDOW_MS 境界で tick が誤爆【修正済み・本命】

- **症状**: ロングトーンが必ず dur ≈ 1019〜1043ms で `delta` 切れ (1 ログで 14 件)。
- **原因**: `CausalEngine::tick()` (ライブ専用の無音監視) が「最後のパルス時刻」として
  `last_uoff_` (ユニーク offset) を使っていたが、これは KRR 窓内 (`offset <= WINDOW_MS=1000`)
  でしか更新されない。ノートが 1 秒を超えると凍結し、弾いている最中でも無音ギャップが
  増え続けて WINDOW_MS + 2Δt で必ず切れる。
- **修正**: 基準を `last_alloff_` (弓速計算用に毎パルス無条件更新) に変更。
  サステインの音量追従は窓外でも `raw_spd_` が更新され続けるので無傷。

### (b) 二重パルスによるタイムアウト崩壊【修正済み】

- **症状**: エンコーダがまれに Δt=2〜3ms の二重パルスを吐く (全ログ横断で実在確認、
  ノート最小 Δt=3ms、通常の Δt 中央値は 11〜15ms)。
- **原因**: tick のタイムアウト基準 `d_ref = deltas_.back()` (直近 1 個) が二重パルスで
  2ms になると、タイムアウトが 2×2=4ms に崩壊 → 次の正常パルス (10〜20ms 後) を
  待てずに切れる。
- **修正**: `d_ref = 末尾 3 個の max`。単発の極小 Δt を無視し、正常時は挙動不変。

### (c) feed 比カットの誤発火 (再アタック)【未修正・意図的に温存】

- 二重パルス直後の本物パルスで `d_new/d_prev > DELTA_RATIO_CUT(2.0)` が成立し、
  ニセ境界 → NoteOff→即 NoteOn の再アタック。音は途切れないがアタックがかかり直す。
- これは論文 2.2.3 の「ノート内誤発火」として定量済み (検証 16 テイクで誤発火 57 件、
  うち分母 Δt≤3ms の二重パルス由来は 13 件 / 23%)。causal エンジン本体 = parity 拘束
  領域のため温存。対処するなら HID 入力段デバウンス (エンジン非接触) だが、
  2.2.3 の評価条件と実機がズレるため実装章への明記が必要になる。

**tick() は Python 因果リファレンスに対応物が無く parity 非拘束** — (a)(b) の修正は
実機の切れ味だけを変え、parity ゲート・論文の数値には一切影響しない (PASS 3 + 既知
CHECK 1 のまま不変)。

## 2. KRR 推論の高速化 (44%)

- **実測 (修正前)**: infer はノート内パルス番号 k にほぼ線形で増加、~72µs/パルス。
  65 パルス目で最大 4.8ms。原因は `score_at_k` が毎パルス 129 SV × (k+1) 次元を
  フル再計算 (プレフィックスごとにスケールが違うため増分計算は不可能) + 内側ループの
  FP 除算 + 1.3MB テーブルのフラッシュ XIP キャッシュミス。
- **対策**: `1/KRR_SCALE` を初回に前計算 (5460 float ≈ 21.8KB、RAM 常駐) して除算→乗算。
- **効果**: 72 → **45µs/パルス** (同規模ノートの mean 2.5ms → 1.4ms、max 4.7 → 2.9ms)。
  parity: 変更前後で誤差が完全一致 (max err 0.002 expr)。
- **残る支配項**: `std::exp` 129 回/パルス。T_CAP=104 での理論最悪は ~4.7ms で、
  現行パルスレート (最短 6ms 間隔・中央値 15ms) に対し実用上は問題なし。
  さらに削るなら SV の距離足切り (枝刈り) が parity 安全寄りの次候補。

## 3. その他の実機修正

- **note_num=0 ゲート**: 鍵盤なし (dataSender の無音) の弓パルスが「ノート 0 (C-1)」と
  して NoteOn まで送られていた。HID poll 段で `note_num==0` を完全無視に (main.cpp)。
  エンジンのノート通番はその分飛ぶが正しい挙動。
